# 实习第一天，我画的**功能结构图**被大厂前辈打回了 3 次

一篇讲透：是什么、和另外两张图啥区别、四步怎么写、微信拆解案例 👇

::: blue 一句话定义
功能结构图 = 以**功能模块**为类别，介绍模块下各**功能组成**的图表——只管"有什么功能"，不管长什么样。
:::

### 📖 这一篇你会拿到
- 功能/信息/产品**结构图三姐妹**一次分清
- 四步写出合格的功能结构图 + **主模块划分秘诀**
- 微信真实模块**拆解案例** + 末页领完整示例

---

## 为什么**这么重要**

实习第一天，我兴冲冲把画好的图发给带教老师，回我一句：

> 「你这不是结构图，是页面目录。**重写。**」

改到第 3 版才过。后来才懂：需求评审时，**开发第一个看的就是这张图**——

- 它决定了开发怎么**评估工作量**
- 它决定了你的功能设计**有没有漏、有没有重**
- 它是 PRD 的**骨架**，骨架歪了细节全白写

::: yellow 💡 记住
功能结构图画得好 = 你真的想清楚了产品。这是**新人最容易露怯、也最容易加分**的一张图。
:::

---

## **它是什么**

一句话：按照**功能的从属关系**画成的图表，图里每个框都是一个功能模块。

- 表达功能之间的**从属关系**：谁包含谁、谁属于谁
- 体现产品的**功能模块**与逻辑结构：一个产品由哪几块拼成
- **不画字段细节**：只管"有什么功能"，不管"长什么样、存什么数据"

> 类比：功能结构图是产品的**骨架 X 光片**——只看骨骼结构，不看皮肤和衣服。画它不需要设计功底，一个树状大纲就够，Xmind / ProcessOn 都能画。

## 先分清**三姐妹**

写 PRD 常见三张图，别再傻傻分不清：

| 图 | 关注什么 | 回答什么问题 |
| --- | --- | --- |
| 功能结构图 | 功能的从属关系 | 产品**有哪些功能**？ |
| 信息结构图 | 数据的分类组合 | 产品**有哪些信息**？ |
| 产品结构图 | 功能 + 信息放回页面 | 每个**页面长啥样**（原型简化版）？ |

::: blue 绘制顺序
功能结构图 → 信息结构图 → 产品结构图。功能框架定了，才谈信息；都齐了才画原型。
:::

## 能用来**干嘛**

| 场景 | 具体用法 |
| --- | --- |
| 🧭 引导方案设计 | 模糊的设计要求，用它变清晰；先定骨架再填页面 |
| 🧹 梳理页面功能 | 鸟瞰全产品，防止功能点**缺漏** |
| 🔍 产品分析 | 竞品功能盘子一图看全 |
| 📦 开发评估 | 开发按模块估工作量，吵不起来 |

::: yellow 💡 使用时机
新项目立项、接手陌生产品、写竞品分析——**动笔之前先画它**。
:::

## **四步写法**

1. **梳理业务流程** 🔍 先想清楚用户从头到尾怎么用：浏览 → 加购 → 下单 → 支付
2. **提炼主功能模块** 🧩 流程里的核心环节 = 候选主模块，画完再走查一遍流程防遗漏
3. **画层级树** 🌳 主模块 → 子功能 → 功能点，一层层往下拆
4. **动词+名词命名** ✍️ 写「设置名字」而不是「名字」——传达准确，看图人不困惑

> 判断标准：每一层**粒度一致**、同一层**不重不漏**（MECE）。

---

## 主模块**怎么定**

- **数量 5–9 个为佳**：太多说明拆太碎，太少说明没想清
- **Tab ≠ 主模块**：产品被迫塞进 3–4 个 Tab 是妥协；功能复杂时按 Tab 分就太粗糙了
- **拆分秘诀** 💡：一个次级功能模块**反复出现在不同 Tab** 里（比如微信的「搜索」），说明它业务上很重要——把它拆出来当主模块，图更简洁

::: blue 两种场景
设计新产品：从业务流程提炼主模块；分析已有产品：参考 Tab 起手，再用自己的语言修正。
:::

---

## 颗粒度**怎么定**

没有标准答案，**由场景决定**：

- 设计阶段：从粗到细，**逐步收敛**——先只画模块，设计推进中拆到具体功能操作
- 汇报/评审：拆到对方能看懂为止，不追求一次到底

| 层级 | 例子 |
| --- | --- |
| 产品 | 微信 |
| 主模块 | 支付 |
| 功能点 | 转账 |
| 操作级 | 转账给好友 · 转账到银行卡 |

> 拆多细看你的汇报对象：给老板看主模块，给开发看操作级。

## **踩坑黑名单**

1. **画成页面目录** ❌ 按 Tab 页罗列页面 ≠ 按功能拆解
2. **粒度乱跳** ❌ 上一层是模块，下一层突然写到按钮文案
3. **重漏交叉** ❌ 「退款」同时挂在订单和支付下面，开发直接来问你
4. **塞满字段细节** ❌ 结构图不是数据库设计，字段留给 PRD
5. **名词式命名** ❌ 写「名字」没人懂是看还是改，写「**设置名字**」就清楚了

> 中枪两条以上的，回去重画——开发一眼就能看出来。

## 案例：**微信支付**拆解

| 模块 | 功能点 | 用户动作 |
| --- | --- | --- |
| 收付款 | 收款码 · 付款码 · 赞赏码 | 我要收钱 / 我要付钱 |
| 转账 | 转账给好友 · 转账到银行卡 | 我要把钱给别人 |
| 钱包 | 零钱 · 零钱通 · 银行卡 | 我要管我的钱 |
| 生活服务 | 手机充值 · 生活缴费 | 我要交电费话费 |

> 注意命名全是**动词+名词**的用户动作视角——「我要收钱」，不是「收款码页面」。

## **动手清单**

画完对照这 7 条：

1. ✅ 从业务流程出发，不是从页面菜单出发
2. ✅ 主模块 5–9 个，层级 3–4 层
3. ✅ 同层功能**不重不漏**，粒度一致
4. ✅ 命名用**动词+名词**，不用页面名、不用裸名词
5. ✅ 反复出现的次级模块，考虑拆成主模块
6. ✅ 不含字段、样式、交互细节
7. ✅ 拿给开发看一遍，能 30 秒讲明白

::: yellow 💡 自检
把图盖住名字，让别人猜这是什么产品——猜得出来，就画对了。
:::

---

## **总结**

功能结构图 = **业务流程 → 主模块（5-9 个）→ 功能点** 的三层树，命名一律**动词+名词**。

它是你产品思维的**第一张可视化答卷**：新人靠它露怯，也靠它加分。

::: blue 🧭 万能公式
梳理流程 → 提炼主模块 → 画层级 → 动词+名词命名 → 不重不漏
:::
