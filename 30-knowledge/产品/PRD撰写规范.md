# PRD 撰写规范

## 一句话本质

PRD 不是写作练习，而是**把"想清楚的问题 + 解法"文档化，让开发/测试/设计达成共识、避免扯皮延期**——产品经理的设计图纸。

## 核心框架

### 1. 动手前：RTPA 逆向思维

假设用户提的初始需求是**错的**，重新发现问题。

> 例：用户反馈"退款慢" → 表层方案"退款可视化进度条" → 逆向追问"为什么要可视化？" → 事实调查发现真问题：退款规则不明确、客服受理慢、审批时间长 → 针对真问题提方案。

配套的**开工七问**：
1. 解决什么问题？
2. 如何衡量解决？（指标 + 埋点 + 谁运营）
3. 多少资源投入？
4. 会不会太复杂？（**复杂是产品的坟墓**——有无性价比更高的方案？影响现有业务/历史数据吗？）
5. 有风险吗？
6. 有创新吗？

### 2. 写作三步走

| 步骤 | 动作 | 产出 |
|------|------|------|
| 搭框架 | 梳理角色画像（用户/运营/开发/运维），划分功能结构 | 功能架构图。层级：**系统 > 功能模块 > 功能**；用户+功能=用例，用例占 PRD 篇幅 70%+ |
| 定流程 | 把角色和功能串成完整业务链路 | 核心业务流程图 + 子流程（活动图、状态机图、外部系统交互、时序图） |
| 做细节 | 原型与交互设计 | 原型图 + 元素说明（是否为空/初始内容/默认值/字数限制），考虑表结构 |

### 3. 文档结构（默认模板）

修订记录 → 全局说明（名词解释/异常处理/默认规则）→ 项目背景（**价值模型→现状→方案→目标**，四段闭环）→ 项目范围（功能结构图）→ 业务流程 → 功能需求（用例为核心：描述 / 前后置条件 / 页面交互 / 业务流程 / **异常与分支流程**）→ 非功能需求（数据埋点 / 监控 / 性能并发）

## 我的调用场景

- **面试**："你如何做需求分析" → RTPA + 退款案例；"PRD 包含什么" → 默写第 3 节结构图
- **作品集**：任何产品拆解/方案文档按此结构组织，体现专业度
- **实习**：接到需求先过一遍七问，写 PRD 时用第 3 节当 checklist
